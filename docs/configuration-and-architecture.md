# Configuration and architecture

How the firmware is configured, why the relay channels are set up the way
they are, and how to extend the system without touching its core.

---

## 1. The big picture

```
                      +-------------------- main (composition root) --------------------+
                      |  reads Kconfig, checks pins at compile time, creates and wires  |
                      +----------------------------------------------------------------+
                         |                 |                  |                  |
                         v                 v                  v                  v
UART bytes --> uart_link --lines--> [queue] --> app_fsm --replies--> uart_link --> UART
              (IDF UART driver,               (state machine,
               line_assembler)                 sole owner of relays)
                                                  |        |
                                          protocol.h    relay_bank.h  (N relays)
                                          (parse/format)    |
                                                         relay.h  (interface)
                                                            |
                                                  relay_gpio  -->  pin_hal.h  -->  pin_hal_esp
                                                  (any future relay type plugs in here)
```

| Rule | Where it shows |
|---|---|
| Each module has one job | Parsing (`protocol`), transport (`uart_link`), relay mechanics (`relay_*`), policy (`app_fsm`), wiring (`main`) |
| Depend on interfaces, not implementations | `app_fsm` only sees `relay.h`, `relay_bank.h`, `link_if.h`, `protocol.h` |
| Hardware is injected | GPIO via `pin_hal_t`, UART via `link_tx_t`, timing via a delay function |
| Pure C core, host-testable | `protocol`, `relay_gpio`, `relay_bank`, `line_assembler`, `app_fsm` contain no ESP-IDF calls |
| Only `main` reads `sdkconfig` | Every other module receives plain config structs |

## 2. Where configuration lives

| What | Where | Changed by |
|---|---|---|
| Firmware version | `PROJECT_VER` in the top-level `CMakeLists.txt` (the only place) | editing that line |
| Board settings (relays, UART, tasks) | `main/Kconfig.projbuild` → menu **IGNACC Controller** | `idf.py menuconfig` |
| System defaults (console off, logs off, 1 kHz tick) | `sdkconfig.defaults` | editing the file |
| Generated result | `sdkconfig` / `build/config/sdkconfig.h` (git-ignored) | generated by the build |

All values are fixed at **build time**. Nothing is configurable at runtime, so
a wrong value can't be sent to a running board.

## 3. The relay channel model (what's different here)

A typical ESP-IDF project hard-codes "relay 1 = GPIO26, relay 2 = GPIO27" in C.
Here the channel count is a setting, and the rest of the firmware adapts to it.

### 3.1 Kconfig: a count plus one pin per channel

```
IGNACC Controller → Relays
    Number of relay channels      (1..14, default 2)
    IN1 relay GPIO                (default 26)
    IN2 relay GPIO                (default 27)   shown when count >= 2
    IN3 relay GPIO                (default 25)   shown when count >= 3
    ...
    IN14 relay GPIO               (default 23)   shown when count >= 14
    Relay active level            (active-low / active-high)
    Relay settle delay (ms)       (default 15)
```

Each GPIO entry uses a **conditional prompt**:

```kconfig
config IGNACC_RELAY3_GPIO
    int "IN3 relay GPIO" if IGNACC_RELAY_COUNT >= 3
    range 0 33
    default 25
```

The `if` hides the prompt in menuconfig, but the symbol **still exists** with
its default value. So `sdkconfig.h` always defines all 14 macros
`CONFIG_IGNACC_RELAY1_GPIO` … `CONFIG_IGNACC_RELAY14_GPIO`, whatever the count.
This is deliberate: C code can then list all 14 unconditionally, without 14
`#if` blocks. Only the first `CONFIG_IGNACC_RELAY_COUNT` entries are used.

The 14 defaults are exactly the 14 safe pins (see 3.3), so raising the count
never gives you an unsafe default.

### 3.2 main.c: one list, three compile-time checks

`main.c` turns the macros into a table with an X-macro:

```c
#define IGNACC_RELAY_GPIO_LIST(X) \
    X(1, CONFIG_IGNACC_RELAY1_GPIO)  X(2, CONFIG_IGNACC_RELAY2_GPIO) ... X(14, CONFIG_IGNACC_RELAY14_GPIO)

#define RELAY_GPIO_ENTRY(ch, gpio) gpio,
static const int s_relay_gpios[] = { IGNACC_RELAY_GPIO_LIST(RELAY_GPIO_ENTRY) };
```

The same list generates the checks, applied only to channels in use:

| Check | How | Build error |
|---|---|---|
| Pin is safe | `static_assert(ESP32_RELAY_PIN_IS_SAFE(gpio))` per channel | `IN3 GPIO is not a safe relay pin` |
| Pin isn't a UART pin | compares against `CONFIG_IGNACC_UART_TX/RX_GPIO` | `IN3 GPIO overlaps the UART pins` |
| No two channels share a pin | ORs one bit per used pin into a 64-bit mask; the number of set bits (`__builtin_popcountll`) must equal the channel count | `Two relay channels use the same GPIO` |

A bad configuration **fails the build on your PC**. It can't reach the bench.
All three errors were verified by deliberately breaking `sdkconfig`
(duplicate GPIO, strapping pin GPIO2, GPIO14 on a third channel).

At start-up, `app_main` loops over the first `CONFIG_IGNACC_RELAY_COUNT`
entries, creates one `relay_gpio` per channel (each latched OFF before its pin
becomes an output) and hands them to the state machine as a `relay_bank_t`.

### 3.3 Why 14 is the maximum

`components/relay/include/esp32_relay_pins.h` defines the safe pins for an
ESP32-WROOM-32:

| Pins | Status |
|---|---|
| 4, 13, 16, 17, 18, 19, 21, 22, 23, 25, 26, 27, 32, 33 | **Safe**: 14 pins |
| 0, 2, 5, 12, 15 | Strapping pins, read at reset (a relay could click, or the chip could boot wrongly) |
| 1, 3 | UART0, the protocol link |
| 6–11 | SPI flash |
| 14 | PWM output during boot |
| 34–39 | Input only |

A host unit test (`test_relay_bank.c`) checks this list against all 40 GPIOs.

### 3.4 How the rest of the firmware adapts

| Layer | Knows the channel count? | How it adapts |
|---|---|---|
| `protocol` | No | Accepts `IN1`..`IN16`, formats `STATUS` for any count |
| `relay_bank` | Holds it | `set_all` / `all_are` loop over however many relays it holds |
| `app_fsm` | Reads it from the bank | Ignores `IN<n>` above the count; `STATUS` lists exactly that many |
| `main` | Yes, from Kconfig | Creates that many relays |

On a 2-channel build, every command and reply is byte-for-byte the same as in
firmware 1.0.0, so existing CAPL scripts keep working.

## 4. Other settings

| Menu → setting | Default | Notes |
|---|---|---|
| Relays → Relay active level | Active LOW | Pin level that switches a relay ON |
| Relays → Relay settle delay (ms) | 15 | Wait before `_OK` (relay operate time ≤ 10 ms + bounce). `ALL_ON/OFF` waits once, not once per relay |
| UART link → UART port number | 0 | UART0 = the devkit's USB bridge |
| UART link → Baud rate | 115200 | 8N1, no flow control |
| UART link → UART TX / RX GPIO | 1 / 3 | Relay pins must not overlap these |
| UART link → RX ring buffer size | 256 | Must be > 128 (hardware FIFO) |
| UART link → Event queue length | 16 | |
| UART link → Maximum command line length | 32 | Longer lines are discarded entirely |
| Tasks → Command queue depth | 4 | Lines waiting for the state machine; when full, extra lines are dropped |
| Tasks → UART RX / state machine priority | 10 / 9 | |
| Tasks → UART RX / state machine stack | 3072 / 3072 | |

`sdkconfig.defaults` also sets: console output **none**, application and
second-stage bootloader logs **off** (UART0 carries only the protocol), and a
**1 kHz** FreeRTOS tick (so a 15 ms settle isn't rounded to 10 ms steps).

## 5. Extending without modifying the core

| You want | What to do | Core changes |
|---|---|---|
| 3–14 relays | menuconfig: set the count and the new channels' pins | none |
| Active-high relays (e.g. transistor drivers) | menuconfig: Relay active level | none |
| Relays on an I/O expander (MCP23017, PCF8574) or shift register | New file `relay_<chip>.c` implementing `relay_t` (`set`, `is_on`); create those relays in `main` and add them to the same array | none: `protocol`, `relay_bank` and `app_fsm` are untouched |
| More than 16 channels | Raise `PROTO_MAX_CHANNELS` and `PROTO_RESPONSE_MAX` in `protocol.h` | two constants |
| A different transport (e.g. UART1 with an external adapter) | menuconfig: UART port and pins | none |

The core modules don't need to change for any of these, because they only
depend on interfaces (`relay_t`, `relay_bank_t`, `link_tx_t`) and plain
config structs.

## 7. API reference

Every public header in `components/*/include/` carries Doxygen comments:
`@file` overview, `@param`/`@return` on every function, documented struct
fields and enum values. To generate HTML, install Doxygen, then run from the
project root:

```bash
doxygen -g Doxyfile
```

Then set these in the generated `Doxyfile` and run `doxygen`:
- `INPUT = components`
- `RECURSIVE = YES`
- `OPTIMIZE_OUTPUT_FOR_C = YES`
- `EXTRACT_STATIC = YES`
